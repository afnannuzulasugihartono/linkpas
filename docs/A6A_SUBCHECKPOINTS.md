# A6a split for current release-candidate validation

The original A6a checkpoint was split before execution after the signed A5 APK was found to predate D4a/D4b Android-wrapper changes.

## A6a1 — Rebuild current signed release candidate

Scope:
- Build an unsigned release APK from the current `main` Android source after D4/D5.
- Sign it with the existing A4 release signing identity outside Git.
- Verify signature/certificate identity, package/version, checksum, and presence of the native D4 diagnostics code.
- Do not perform install/TWA acceptance in this checkpoint.

Acceptance:
- Release APK is rebuilt from Android source equivalent to current `main`.
- APK is signed with the same release certificate fingerprint already published in Digital Asset Links.
- Package is `id.barangpas.linkpas` and version is `0.1.0-beta` / code `1`.
- APK signature verification passes.
- A new SHA-256 checksum is recorded.
- APK contains the native D4 diagnostics implementation and `ManageDataLauncherActivity` manifest declaration.
- Signing keystore/password remain outside Git and are not exposed in logs.

Status: COMPLETE.

## A6a2 — Automatic install/App Links/TWA acceptance without routine ADB

A6a2 is split again before implementation because native self-verification, browser Digital Asset Links validation, fallback detection, signed rebuild, and real-device evidence cannot reasonably fit inside one 18-minute checkpoint.

Normal path must not require the user to run ADB. ADB remains a last-resort fallback only when public Android/browser evidence is genuinely inconclusive.

### A6a2a — Native self-check primitives

Scope:
- Add a Beta-only native self-check collector without changing normal LINKPAS product behavior.
- Read the installed signing certificate SHA-256 using Android package/signing APIs and compare it with the expected release fingerprint.
- On Android 12+ read `DomainVerificationManager` state for `linkpas.vercel.app`; distinguish verified from user-selected/unsupported/unknown states.
- Discover the selected/available browser provider and whether a provider advertises Trusted Web Activity capability.
- Emit only sanitized technical metadata through the existing diagnostics transport.
- Add bounded unit tests for mapping/sanitization and unsupported API behavior.

Acceptance:
- Android unit tests pass.
- Self-check payload reports signer match, App Links state, Android SDK, browser provider, and TWA-capability state without user content/device identifiers/secrets.
- Android < 12 is reported as `unsupported_api` rather than guessed.
- Normal launch path remains unchanged.

Target: 12-15 minutes. Hard stop: 18 minutes.

### A6a2b — Browser DAL validation and fallback evidence

Scope:
- Bind to the chosen Custom Tabs/TWA-capable browser provider.
- Use a browser session relationship validation for `delegate_permission/common.handle_all_urls` against `https://linkpas.vercel.app`.
- Record callback result as tri-state `true`, `false`, or `timeout/inconclusive`; a timeout must not be converted into a false failure.
- Instrument the Android Browser Helper fallback strategy so actual Custom Tab fallback records `fallback_invoked=true` before handing off.
- Record TWA launch-request/fallback evidence without adding user-visible product UI.

Acceptance:
- Browser relationship result and fallback state are available as sanitized diagnostics metadata.
- Explicit relationship `false` is distinguishable from callback timeout.
- Actual fallback invocation can be observed without ADB.
- No normal-user data, clipboard content, link content, signing material, or device identifier is collected.
- Android unit/build checks pass.

Target: 12-15 minutes. Hard stop: 18 minutes.

### A6a2c — Automatic PWA handshake and verdict correlation

Scope:
- Add a short-lived random technical launch probe ID generated by the Android wrapper for Beta verification runs only.
- Pass the probe to the LINKPAS origin, remove it from visible browser history/state immediately on the PWA side, and automatically emit a sanitized PWA runtime probe report.
- Correlate native self-check and PWA runtime evidence by probe ID in Supabase.
- Define deterministic verdict rules: `PASS_VERIFIED_TWA`, `FAIL_FALLBACK`, `FAIL_DAL`, `INCONCLUSIVE`, and `NEEDS_ADB`.
- Keep the existing manual diagnostics panel functional, but routine A6a2 verification should not require pressing `Kirim laporan diagnostik`.

Acceptance:
- One verification launch can produce correlated native + PWA reports without screenshot or ADB.
- Probe IDs contain no user data and are bounded/ephemeral.
- PWA runtime report confirms app load/service-worker state for the same probe.
- Verdict logic never promotes timeout/unknown evidence to PASS.
- Existing web tests/build remain green.

Target: 12-15 minutes. Hard stop: 18 minutes.

### A6a2d — Rebuild and sign automatic-diagnostics RC

Scope:
- Build a release candidate containing only the A6a2a-c verification instrumentation plus prior accepted product code.
- Sign with the existing A4 release identity outside Git.
- Verify package/version, signature/certificate, checksum, and presence of the new self-check implementation.
- Produce the installable APK used by A6a2e.

Acceptance:
- Release build/tests pass.
- APK signature verifies with the published LINKPAS release certificate fingerprint.
- Package remains `id.barangpas.linkpas`; release identity does not drift unexpectedly.
- A fresh SHA-256 checksum is recorded.
- No signing secret is committed or exposed.

Target: 12-15 minutes. Hard stop: 18 minutes.

### A6a2e — Real-device automatic acceptance

Scope:
- User installs/updates the A6a2d APK and opens LINKPAS normally; no user-run ADB, screenshot, or manual debug commands are part of the normal path.
- Read the resulting correlated native/PWA reports from Supabase.
- Evaluate signer, App Links, TWA-capable provider, browser DAL relationship, fallback state, PWA handshake, and launch health against the deterministic verdict rules.
- Consult existing diagnostics for any failure.

Acceptance:
- `PASS_VERIFIED_TWA` requires all mandatory positive evidence and no fallback evidence.
- `FAIL_FALLBACK`/`FAIL_DAL` records a precise blocker and does not claim APK readiness.
- Browser callback timeout or unavailable public evidence yields `INCONCLUSIVE`, not guessed PASS/FAIL.
- `NEEDS_ADB` is allowed only after automatic evidence is exhausted; ADB is not the routine path.
- On PASS, A6a2 completes and the next checkpoint is A6b.

Target: 12-15 minutes. Hard stop: 18 minutes.
